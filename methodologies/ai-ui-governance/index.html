AI 辅助 UI 治理：从问题诊断到主题、组件与资产迁移

一套把 AI 从“改页面工具”变成可审计、可验证、可迁移的真实业务工作流。

Linpo Wu2026

AI 已经可以修改 CSS、补齐组件状态、调整响应式布局，也可以根据一套设计规范重做界面。真正困难的部分随之发生了变化：设计师如何让 AI 理解项目现状，如何控制修改范围，又如何确认改完以后真的更好。

这类工作可以称为 UI 治理。它关注的不只是某个页面是否好看，还包括视觉规则是否一致、组件使用是否健康、交互状态是否完整、主题能否切换、旧资产能否迁移，以及设计规则能否长期被团队采用。

AI 负责扫描、归纳、生成方案、执行受控修改和运行检查。设计师、产品经理和前端工程师仍然负责规则、取舍、业务边界和最终验收。

本文把 UI 治理拆成一条可执行的工作流，提供一个不要求技术背景的计划模式入口，再由 AI 为九个常见场景生成技术执行计划，并补充三个经常被遗漏的长期治理机制。提示词不是独立的“咒语”，每组都要放回项目事实、权限、产物和验收的上下文中使用。

一、先理解 UI 治理的范围

UI 治理不是把所有页面改成同一种样式，也不是把扫描出来的每个异常值都替换掉。它更接近一套持续维护机制：先知道项目当前的事实，再判断哪些偏差值得处理，最后用可回归的方式完成修改。

一个可以长期运行的治理流程，至少要同时看四件事：

维度需要回答的问题常见证据
视觉颜色、排版、间距和布局是否有稳定规则token、样式文件、页面截图
组件组件语义、API、状态和粒度是否健康JSX/TSX、组件文档、运行页面
运行主题、响应式、键盘和错误状态是否可用多视口截图、交互路径、对比度检查
生命周期新旧规范、资产和文档如何迁移与废弃版本记录、迁移清单、采用率数据

因此，UI 治理的对象已经超过了“视觉代码”。它是一套从规范到代码、从页面到组件、从当前版本到迁移过程的维护工作。

二、统一闭环：诊断、分流、试点、验证、沉淀

九个场景是任务入口，不是九个固定步骤。更稳定的执行顺序是：

建立基线
  ↓
视觉与组件双轨诊断
  ↓
人工确认问题、例外和优先级
  ↓
选择治理路径
  ↓
小范围试点
  ↓
代码、视觉与交互验证
  ↓
批量推广或回退
  ↓
规则、文档和迁移记录沉淀

1. 建立基线

先记录项目技术栈、组件库版本、主题入口、关键路由、目标视口、设计规范来源和已有验证命令。能运行项目时，保存关键页面的基线截图；无法运行时，明确标记“只有代码证据，没有页面证据”。

2. 双轨诊断

视觉审计和组件审计可以并行运行。前者查看样式、布局、响应式风险，后者查看语义标签、组件 API、可访问性和组件粒度。两份报告都只提供证据和候选问题，不直接宣布所有异常都是缺陷。

3. 人工分流

由设计师、产品经理和前端共同确认：哪些问题要立即修复，哪些属于合理例外，哪些需要产品规则，哪些应该进入迁移计划。输出执行范围、优先级、风险等级和停止条件。

4. 试点与推广

基础组件、主题变量和公共 API 的改动先选择一到三个代表性页面试点。试点通过后再拆成独立批次扩展，不把“全项目改造”当成一次不可回退的操作。

5. 验证与沉淀

运行静态检查、构建和相关测试，保存多视口截图，实际操作关键路径，并记录未覆盖项。确认后的规则、例外、迁移映射和版本变化要回写到项目文档或 Skill 中。

场景编号是稳定的任务 ID，不表示执行顺序。场景 8 和场景 5 也不是同一件事：场景 8 主要处理 token 和主题基础设施，场景 5 主要处理页面、组件和整体视觉表现。场景 9 内部再分为资产迁移与组件 API 迁移，两者的验证重点不同。

三个经常遗漏的长期治理机制

这三项不再额外编号为“场景”，因为它们贯穿九个执行场景，属于设计系统的长期运行机制。

治理机制解决的问题建议频率关键产物
设计稿—代码漂移审计Figma/设计文件与线上组件逐渐分叉版本发布或定期抽检漂移清单、优先级、责任人
文档与采用率治理组件已经发布，却没人按规范使用组件发布后持续检查使用率、弃用率、文档缺口
版本与变更影响治理token、组件或资产更新后影响范围不清楚每次版本变更变更日志、影响矩阵、迁移窗口

没有这三项，设计系统很容易出现“规范写在文档里，代码按另一套规则生长”的情况。它们也正是 AI 可以持续协助，但不能独自制定规则的部分。

可以作为专项扩展的领域

无障碍深度测试、国际化与 RTL 布局、字体和资源性能、动效与减少动态效果偏好，都值得治理。但它们需要不同的业务数据、运行环境和验收工具。当前文章把它们列为扩展检查项，不继续扩大场景编号；当项目确实有这些目标时，再为对应领域建立独立提示词和测试基线。

1. 定点热修复修复 [文件/组件] 的 [可复现问题]，限制修改范围并验证最小改动与验证记录
2. 交互体验补全审计点击、异步、键盘和错误状态的缺口，只出方案交互缺口清单
3. 智能视觉审计扫描样式、布局、颜色、排版和响应式风险，只出报告视觉问题地图
4. 老旧代码提纯基于事实基线提取语义变量，保持视觉结果token 映射与分批计划
5. 设计系统对齐在试点范围内对齐目标设计系统，保留业务 API规范差异与试点改造
6. 响应式适配治理复现指定视口的溢出和坍塌，先定位再修复响应式修复计划

这张表只用于选入口。真正执行时，仍然要补上项目输入、允许范围、停止条件和验证命令。

四、选择 AI 的授权等级

工具可能叫 Standard、Plan、Goal，也可能使用别的名称。真正需要控制的是 AI 的授权范围：

授权等级AI 可以做什么适用任务
直接执行在明确文件和行为范围内修改并验证定点热修复、已确认的单文件修复
只分析后确认先提交证据、方案和风险，不改代码交互审计、视觉审计、组件审计、响应式定位、迁移规划
有界自主执行在目录、规范、检查点和停止条件内分批推进设计系统试点、Token 注入、已批准的批量迁移

任务越大，边界越要具体。目录、不可修改项、设计规范版本、验证命令、批次大小和停止条件都应写进提示词。不要用一句“把全项目改好”代替项目事实。

场景与授权建议

场景首选授权原因
1. 定点热修复直接执行问题、文件和期望效果都已明确
2. 交互体验补全只分析后确认状态背后可能有产品规则
3. 智能视觉审计只分析后确认需要区分异常候选与合理例外
4. 老旧代码提纯只分析后确认影响面广，需要建立基线和变量语义
5. 设计系统对齐有界自主执行适合试点后分批推进，不能无边界全量修改
6. 响应式适配治理只分析后确认必须先真实复现，并回归相邻视口
7. 组件规范审计只分析后确认语义和 API 问题需要结合项目封装判断
8. 主题与 Token 适配只分析后确认token 映射、对比度和主题回退需要人工确认
9. 资产与废弃组件迁移只分析后确认路径、Props、回调和资源匹配不能盲目覆盖

即使使用有界自主执行，也应把任务拆成可回退的批次。授权等级描述的是修改权限，不代表 AI 可以跳过试点和验收。

五、先用计划模式认识项目

如果你是 UI 设计师，或者还不熟悉这个项目，不需要先填写技术栈、文件路径和命令。先把下面这段提示词复制到 AI 的计划模式中，再用日常语言描述你想解决的事情。

设计师可直接使用的两阶段计划提示词

你现在处于计划模式。请先了解项目，再帮我制定 UI 治理计划；本轮不要修改文件、执行可能改变项目的操作、提交或发布。

请严格分成两个阶段：
- 阶段一是“确认计划”：认识项目、整理证据、列出方案，等我确认后再继续。
- 阶段二是“执行准备或执行”：只有在我确认范围和方案后，才可以生成具体执行计划；只有我再明确回复“执行”后，才可以修改文件。当前对话有项目访问和修改权限时，按计划分批执行；没有权限时，生成可交给前端或工程师的执行清单。
- 阶段一不能假装已经得到文件、页面或运行结果；事实不全时先标记待确认。

我是 UI 设计师，不一定懂技术术语。请遵守这些规则：
- 先查看项目说明、目录结构、页面入口、设计规范和已有运行方式。不要让我凭空填写技术栈、文件路径或命令。
- 如果你无法看到项目文件或打开页面，请明确告诉我缺少什么，并用“请上传项目压缩包/相关文件/页面截图或链接”的方式指导我补充；不要假装已经检查过。
- 用简单中文告诉我：这是一个什么项目、目前能看到哪些页面、你找到哪些设计规则，以及哪些信息还无法确认。
- 我说“按钮太挤”“页面不统一”“手机上放不下”时，请先翻译成可检查的问题，再告诉我可能的影响；不要直接把猜测说成事实。
- 每次最多问我 3 个必要问题，并说明每个问题会影响什么决定。没有答案的字段先标记为“待确认”，不要编造。
- 阶段一先给我一个设计师能看懂的确认计划。技术术语第一次出现时要用一句话解释，不要把技术猜测写成结论。
- 阶段一必须包含：项目概况、已确认的证据、待确认的信息、建议处理范围、不处理的内容、可选方案、风险、需要我决定的事项和下一步。
- 阶段一结尾必须明确写“等待确认”，不要直接输出可开工的代码任务。
- 只有我确认后，才进入阶段二的执行准备。真正修改文件前，还必须收到我的“执行”回复，并确认：具体页面、组件和文件、前置材料、按顺序排列的修改步骤、每步产物、批次范围、验证命令或人工检查、验收标准、停止条件和回退方式。
- 阶段二中不能使用“可能涉及的文件”“再看情况处理”作为最终内容；如果无法确定，先列为阻塞项，不得称为可执行计划。
- 如果项目无法运行，分开写“已从文件确认”和“需要打开页面验证”，不要把代码推测当作页面结果。
- 默认先做审计和小范围试点，得到确认后才建议批量修改。除非我明确说要执行，否则不要修改代码。

我的目标是：[用日常语言描述问题或想达到的效果]
我能提供的材料是：[截图、Figma 链接、页面地址、品牌规范、代码目录；不知道的可以留空]
我最关心的页面或流程是：[页面名称、链接或“暂时不知道”]

这段提示词的作用是建立“先认识项目、再确认问题、最后出计划”的顺序。设计师只需要提供看到的现象和手头材料，不需要先判断它属于 CSS、组件、Token 还是 API 问题。

可以直接这样描述目标：

  • “我想让首页的按钮和其他页面看起来统一，先帮我找出差异。”
  • “手机上这组卡片挤在一起，先判断问题和几种处理方式。”
  • “我想加入深色主题，但不知道项目现在有没有主题变量。”
  • “请找出页面里看起来像旧版本的图标，先做替换计划。”

AI 应先把这些话转换成场景和检查项，再让设计师确认，不要求设计师自己选择场景编号。

九个场景的短指令

下面的句子可以接在通用计划提示词的最后。只需要替换方括号里的日常描述，不需要填写代码术语。

场景可以直接复制的说法
1. 定点热修复请先了解这个项目，帮我制定计划，修复 [页面/截图] 中 [具体现象]。只处理这个问题，不要顺手改其他地方。
2. 交互体验补全请检查 [页面/流程] 里用户点击、等待、失败和完成时有没有清楚的反馈，先给我补全计划，不要改代码。
3. 智能视觉审计请找出 [页面/项目] 中明显不统一或可能影响使用的视觉问题，用截图和简单中文说明，不要把所有不同都当成错误。
4. 老旧代码提纯请帮我找出项目中重复的颜色、字号、间距和样式规则，先制定保持现有外观的整理计划，不要做整体改版。
5. 设计系统对齐请把 [页面/项目] 和 [Figma/品牌规范/参考页面] 做对比，先列出差异和试点计划，保留现有业务功能。
6. 响应式适配治理请检查 [页面] 在手机或平板上出现的 [挤压/遮挡/放不下/横向滚动]，先确认原因和处理方案，不要直接隐藏内容。
7. 组件规范审计请检查 [页面/项目] 中按钮、输入框、弹窗等常用控件是否用法混乱、状态缺失或难以操作，先输出问题清单和计划。
8. 主题与统一样式规则我想给 [页面/项目] 增加 [深色/品牌/高对比度] 主题，请先确认项目现在有没有可复用的颜色和样式规则，再制定试点计划。
9. 资产与废弃组件迁移请找出 [页面/项目] 中看起来已经过时的图标、图片或控件，先建立新旧对应关系和小批量替换计划，不要直接全量替换。

如果设计师只有截图，也可以把“页面”替换成“这张截图”；如果连项目入口都不知道，就写“请先帮我找到可以打开的页面”。

阶段一：设计师确认计划的输出格式

为了让非技术用户能判断计划是否正确，第一轮只输出下面这部分：

【给设计师看的摘要】
- 我理解的目标：
- 我看到的现象：
- 已确认的证据：
- 还不能确认的地方：
- 建议先处理的范围：
- 暂时不处理：

【请你确认】
- 需要你决定的问题：
- 每个决定会影响什么：

【计划】
1. 先检查什么，产出什么
2. 再试点什么，如何对比
3. 通过什么条件后才扩大范围

【本阶段结论】
- 现在可以确认的范围：
- 还不能进入执行的原因：
- 等待我确认：是

确认阶段一后，请让我选择下一步：

  • 回复“执行”：如果当前对话有项目访问和修改权限，就按计划开始分批执行；每批完成后汇报修改和验证结果，遇到停止条件立即暂停。
  • 回复“生成执行清单”：只输出下面的具体执行计划，供前端或工程师接手，不修改代码。

如果我没有确认，继续解释方案或补充问题，不要修改代码。

场景 6：响应式适配治理

什么时候用

页面在特定视口出现横向滚动、内容遮挡、卡片挤压、表格无法阅读或操作区掉出屏幕。先复现，再决定使用宽度约束、换行、滚动、折叠还是信息重排。

技术执行模板（计划确认后使用）

任务：专项治理 [页面/目录] 在 [目标视口] 下的响应式问题。先复现和定位，再输出计划；未经确认不修改代码。

【范围】
- 目标页面：[路由或入口]
- 目标视口：[例如 375、768]
- 桌面回归视口：[例如 1024、1440]
- 只处理：横向溢出、内容遮挡、关键布局坍塌、不可操作区域。
- 不处理：颜色、字体风格、品牌视觉和无关交互重构。

【复现与根因】
1. 在目标视口记录横向滚动、裁切、重叠、异常换行和操作不可达位置。
2. 保存截图或 DOM 证据，定位组件和样式来源。
3. 检查固定宽度、min-width、固定列数、flex 子项 min-width、grid 最小宽度、长文本、媒体固有尺寸、breakpoint 顺序和 absolute/fixed 元素。
4. 页面无法运行时，只标记“风险候选”，不写成已复现问题。

- 不用 overflow: hidden 隐藏仍需阅读或操作的内容。

- 表格根据业务选择横向滚动、列优先级、折叠或卡片化。
- 移动端修复必须做桌面回归，共享样式变更需要检查其他调用页。

【输出格式】
每项包含页面、视口、复现步骤、证据、根因、涉及文件、建议修改、选择理由、其他视口影响、验收条件和人工确认项。

【执行限制】
只输出修复计划，不修改代码。影响桌面端或改变信息层级的方案标记为“需设计确认”。

验收重点

至少检查问题视口、相邻视口和桌面视口，并用长标题、空数据、长数据和多语言内容复查。

场景 3：智能视觉审计

什么时候用

页面已经出现风格分叉，但团队还不能说明问题集中在哪里；或者准备提纯、Token 注入和 Redesign 前，需要先建立事实基线。

技术执行模板（计划确认后使用）

任务：对 [目录范围] 做 UI 视觉与样式治理审计，输出带证据的报告，本轮不修改代码。

【事实来源优先级】
1. 项目已有 Design Tokens、主题变量和组件规范；
2. 已确认的 Figma/品牌规范；
3. 已上线关键页面中的稳定共性；
4. 只有项目明确要求时，才对照 [外部设计系统及版本]。

【审计维度】
一、布局与定位：统计 absolute、fixed、负 margin、固定高度和高 z-index，排除合理浮层；标记可能在内容增长、语言变化或缩放时错位的实现。
二、尺寸与间距：统计 padding、margin、gap、width、height、radius，结合现有 token 判断重复语义；非 4/8 倍数只作为异常候选。
三、色彩：合并大小写、缩写和等价表示后统计硬编码色值、透明度和渐变，区分品牌色、语义色、中性色和数据色板；不按频率直接命名主色。
四、字体：统计 font-family、font-size、font-weight、line-height、letter-spacing 组合，找出同一语义的多套组合；不要为了凑五档字号强行压缩。
五、组件一致性：检查按钮、输入框、卡片、弹窗、标签和表格是否存在无意分叉。
六、响应式风险：检查固定宽高、nowrap、长文本、图片比例和表格容器，能运行页面时在 [视口列表] 记录真实问题。

【过滤与边界】
- 忽略 node_modules、dist、build、coverage 和生成文件。
- 已知合理例外：[填写]。
- 代码异常值不等于页面缺陷；无法确认时降低置信度。
- 只审计视觉和呈现，不修改业务逻辑。

【输出格式】
1. 项目事实摘要；
2. 高、中、低风险总览；
3. 分类型问题清单，每项含文件路径、当前实现、对照规则、影响、证据、置信度和建议；
4. 合理例外与暂不处理项；
5. 建议优先试点的 1—3 个组件或页面。

【执行限制】
只出报告，不修改代码。同源问题可以合并统计，但必须保留可追溯的文件清单。

验收重点

报告至少要回答：问题在哪里、为什么算问题、修复后影响什么。只有“发现很多硬编码值”的统计还没有进入治理。

场景 7：组件规范审计

什么时候用

页面样式看起来相似，但组件语义、API、可访问性或内部复杂度已经开始分叉。此场景只审计 JSX/TSX 和组件使用，不修改业务逻辑。

技术执行模板（计划确认后使用）

任务：对 [目录范围] 进行组件使用规范、语义健康度与可访问性基础审计，只输出报告，不修改代码。

【项目输入】
- 实际 UI 框架及版本：[Ant Design、MUI、自研组件等]
- 标准按钮、链接、表单、弹窗和图标组件：[填写]
- 已知合理例外：[填写]
- 组件文档或规范来源：[填写]

【审计维度】
1. 语义化：找出用 div/span 模拟按钮或链接的交互元素，检查 a 是否有有效 href，检查列表是否使用正确 ul/ol/li 结构。先排除项目已有的语义封装。
2. 框架 API：按实际版本检查高风险 API 误用，例如 Table 缺少稳定 rowKey、Modal 嵌套、Form 字段与校验规则不匹配、size 变体无序扩散。缺少某个属性只能作为风险候选，不能直接判定错误。

- 忽略 node_modules、dist、build、.next、工具函数和生成文件。
- 全局布局中的必要容器不按普通业务组件判定。
- 第三方组件内部不审计，但检查项目是否错误覆盖其 API 或状态。

【输出格式】
按语义、API、A11y、粒度、弃用与重复分组。每项包含文件路径及行号、代码片段、规则依据、用户或维护影响、风险等级、置信度、建议替换方案和是否需要人工确认。

需要结合运行页面、键盘操作和项目组件文档复核。div onClick、文件很长或缺少某个属性都不应被 AI 自动改成统一答案。

八、规则与系统建设组：场景 4、8、5

场景 4：老旧代码提纯

什么时候用

视觉暂时不准备调整，但样式代码大量复制，颜色、间距和字号难以维护。目标是改善结构，尽量保持现有视觉。

技术执行模板（计划确认后使用）

任务：为 [目录范围] 制定视觉代码提纯方案。本轮只建立事实基线、变量模型和分批计划，不直接修改业务文件。

【目标】
- 降低重复硬编码和样式分叉；
- 优先复用已有变量和组件；
- 保持当前视觉与交互结果，暂不进行 Redesign。

【事实基线】
1. 定位主题文件、CSS Variables、SCSS 变量、Tailwind 配置或组件主题配置。
2. 统计 color、background、border、spacing、radius、font-size、line-height 等值及组合。
3. 合并 #fff/#ffffff/rgb(255 255 255) 等等价写法。
4. 区分全局高频、局部高频和单次例外；能运行页面时记录关键视口基线截图。

【语义映射】
- 根据使用位置提出 --color-text-primary、--color-border-default、--color-surface-raised、--space-control-x 等候选。
- 同一个物理值可以对应不同语义变量。
- 无法确认语义的值进入人工命名清单，不按出现次数随意命名。

【分批与验证】
- 按组件或页面拆批，第一批选择高使用量、低业务风险组件。
- 每批列出原值、候选变量、使用语义、涉及文件和预计替换数量。
- 标记图表、活动页、富文本、第三方覆盖等高风险区域。
- 为每批列出静态检查、构建/测试、截图页面、人工状态和停止条件。

【输出要求】
事实摘要、高频值统计、变量表、分批计划、高风险文件、合理例外、验证与回退方案。

【执行限制】
不引入外部设计系统，不为了消除硬编码创建只使用一次且无语义价值的变量。

验收重点

变量数量减少不是唯一目标。要确认同类组件是否共享规则、变量名能否说明用途，以及替换后是否有可回退的视觉基线。

场景 8：主题适配与 Token 注入

什么时候用

设计团队已经提供外部 token 表，需要把它注入现有项目，或者需要建立浅色/深色、品牌换肤和高对比度主题。场景 8 处理的是变量与主题基础设施，页面视觉升级仍属于场景 5。

技术执行模板（计划确认后使用）

任务：基于 [Token JSON/JS 文件] 为 [项目范围] 建立语义化 token 和 [浅色/深色/品牌] 主题。本轮先输出映射与试点方案，不批量修改业务组件。

【Token 输入】
- token 来源和版本：[填写]
- primitive token 与 semantic token 的层级：[说明或要求先分析]
- 当前主题机制：[class、data-theme、prefers-color-scheme 等]
- 目标主题：[light、dark、high-contrast、brand 等]
- 允许修改范围：[填写]

【执行步骤】
1. 读取 token schema，区分原始色值、语义值、组件值和状态值。
2. 建立“现有值/变量 → 新 token → CSS 变量”的映射表；颜色要区分品牌、背景、文字、边框、成功、警告、错误和数据色板。
3. 检查 spacing、radius、typography、elevation 等非颜色 token 的单位、语义和兼容性。
4. 设计浅色与深色覆盖层，说明主题切换机制、默认主题和未定义 token 的回退规则。
5. 检查文字/背景、边框/背景、图标/背景和交互状态的对比度；对比度不足标记“需人工校验”，不自动篡改品牌色。
6. 选择 [1—3 个代表性页面] 试点，检查默认、hover、focus-visible、disabled、loading、error 和图表状态。

【输出要求】
1. token schema 与版本摘要；
2. theme.css/tokens.css 候选定义；
3. 深色或高对比度覆盖文件；
4. 原值 → 新语义变量映射表；
5. 对比度和主题状态风险清单；
6. 试点范围、验证命令、批量推广条件和回退方案。

【执行限制】
只出方案和变量定义，不修改业务组件逻辑。内联样式需要拆出时先列出影响，不直接全量改写。

验收重点

主题切换要在真实页面验证，不能只检查变量文件。浅色与深色都要覆盖组件状态、图表、图片、阴影和边框；对比度报告也不能代替人工检查品牌表达。

场景 5：设计系统对齐与 Redesign

什么时候用

项目已经确认更新视觉规范，目标设计系统、品牌方向、范围和负责人明确。外部系统提供参考，不替团队决定品牌、信息层级和业务场景。

技术执行模板（计划确认后使用）

任务：在明确边界内推进 [项目/目录] 的视觉 Redesign，使其对齐 [目标设计系统、品牌规范及版本]。

【已确认输入】
- 设计规范来源和版本：[填写]
- 品牌不可替换项：[Logo、主色、插画、数据色板等]
- 目标页面、暂不改造页面、代表性试点页面：[填写]
- 需要保留的业务逻辑、数据结构、路由和公共组件 API：[填写]

【阶段一：差异分析】
读取现有 token、基础组件和试点页面，列出颜色、排版、间距、圆角、阴影、布局和交互状态差异，并区分 token 可解决、基础组件需修改和逐页处理的问题。本阶段不改代码。

【阶段二：规范映射】
建立当前规则 → 目标规则的映射，覆盖颜色语义、排版角色、spacing、radius、elevation、基础组件和 hover/active/focus-visible/disabled/loading/error 状态。无法安全映射的值进入人工确认清单。

【阶段三：试点执行】
只修改试点范围，保留业务逻辑和公共 API。每批运行 [命令]，在 [视口列表] 截图，记录预期与非预期差异。达到试点验收点后停止，等待设计与前端确认。

【推广条件】
试点视觉方向已确认、基础组件回归通过、合理例外已登记、剩余页面可拆批、每批都有验证页面和停止条件。

【验证与停止】
静态扫描用于发现未映射值，不以硬编码归零为唯一标准。构建、相关测试和多视口检查通过。规范冲突、公共 API 变化、视觉差异无法解释或超出目录时停止当前批次。

【最终输出】
完成批次、文件清单、token/组件变更、验证结果、合理例外、未完成项、人工决策问题和回退方式。

验收重点

Redesign 的完成标准是规范层级在真实业务页面中成立，并且剩余页面有可控迁移路径，不是所有数字都被强行改成同一组倍数。

九、迁移与清理组：场景 9

场景 9A：图标与图片资产迁移

任务：将 [目录/页面范围] 的旧图标和图片资产迁移到 [目标图标库/资产目录]。本轮只输出迁移计划和首批示例，不批量覆盖业务文件。

【扫描范围】
- <img src>、背景 url()、SVG 内联、旧图标库类名、旧 Icon 组件和动态资源路径。
- 忽略 node_modules、第三方库自带图标和已登记的品牌特殊资产。

【匹配与风险】
1. 建立旧路径/类名 → 新组件或新路径的映射表。
2. 检查名称、语义、视觉重量、线宽、内边距、尺寸、比例和颜色继承。
3. 保持布局尺寸和可操作区域稳定；不同图标库无法保证像素完全相同，差异进入人工复查清单。
4. 检查 alt、装饰性图片 alt=""、懒加载、加载失败和资源许可来源。
5. 无法自动匹配的资产标记为人工映射，不用相似名称盲目替换。

【输出要求】
- 资产映射表
- 组件调用替换示例
- 需要截图复查的页面和视口
- 资源路径、加载和可访问性风险
- 首批迁移范围、回滚方式和人工待确认项

场景 9B：废弃组件与 API 迁移

任务：将 [旧组件列表或 @deprecated 组件] 迁移到 [新组件/API]。本轮先输出影响分析、Props 对照和首批迁移方案，不直接全量替换。

【扫描范围】
- @deprecated JSDoc、旧组件导出、旧 Props、旧事件名、旧样式入口和文档示例。
- 忽略第三方库内部实现，保留项目现有未提交改动。

【影响分析】
1. 列出每个调用点、路由、页面状态和使用频率。
2. 建立旧 Props → 新 Props、旧事件 → 新回调、旧默认值 → 新默认值的对照表。
3. 检查受控/非受控模式、异步状态、表单校验、焦点管理、错误处理和业务回调是否保持一致。
4. 识别无法一对一映射的 API，标记需人工重写的调用点。
5. 设计兼容层、分批迁移和回滚路径，说明何时删除旧组件。

【验证要求】
- 运行类型检查、相关测试和构建。
- 在代表性页面完成默认、加载、错误、禁用和边界数据操作。
- 检查公共 API、路由和埋点是否改变。

【输出要求】
调用点清单、Props/API 对照表、首批文件、测试与截图计划、人工清单、回滚方案和旧组件删除条件。

场景 9 的共同边界

迁移不是查找替换。资产迁移要验证视觉和资源行为，组件迁移要验证状态、回调和 API。两类任务都应先做一小批，确认映射稳定后再扩大范围。

十、三个长期治理机制的提示词

机制 A：设计稿—代码漂移审计

任务：对 [设计文件/组件库/关键页面] 做设计稿与代码实现漂移审计，只输出报告。

请先确认设计文件版本、代码分支、组件映射和比较页面。按颜色、排版、间距、组件状态、内容规则、响应式和交互路径分组。每项列出设计证据、代码证据、差异类型（设计变更、实现缺陷、文档过期或合理例外）、影响、置信度、责任人和建议动作。无法从现有材料确认的内容标记待补证据，不要把截图差异直接判定为实现错误。

机制 B：文档与采用率治理

任务：检查 [组件库/代码仓库] 的组件文档、示例和实际采用情况，输出维护报告，不修改代码。

扫描组件导出、使用次数、废弃标记、文档链接、示例覆盖和常见错误用法。区分“组件不存在”“文档缺失”“文档与 API 不一致”“已有组件未被采用”“业务变体合理存在”。输出使用率、重复实现、文档缺口、弃用风险、优先级、建议补充的示例和需要产品/设计确认的规则。不要以调用次数单独判断组件质量。

机制 C：版本与变更影响治理

任务：评估 [token/组件/资产包] 从 [旧版本] 升级到 [新版本] 的影响，只输出迁移与发布计划。

读取变更日志、导出 API、token 差异、使用方清单和已知弃用项。建立“变更项 → 受影响组件/页面 → 风险 → 验证方式 → 迁移批次”的矩阵。分别标记视觉变化、行为变化、类型/构建变化、性能变化和文档变化。给出兼容层、灰度或回滚方案、旧版本保留期限、删除条件和发布后观察项。无法确认的影响不得写成已验证结果。

这些机制把一次性改造变成可追踪的维护过程。它们适合接入版本发布、组件发布和定期体检，而不是每次临时写一段大提示词。

十一、统一验收、回退与人工确认

四层验收

  1. 静态检查：发现超范围文件、未映射 token、危险选择器、重复实现和弃用引用。
  2. 构建与测试：运行 lint、类型检查、单元测试、构建和相关集成测试。
  3. 多视口视觉检查：对照基线检查布局、尺寸、字体换行、颜色、主题和层级。
  4. 交互与人工验收：实际完成关键任务，检查默认、hover、focus-visible、disabled、loading、error、空数据、权限和键盘路径。

通用验收提示词

请对本次 UI 治理改动进行验收，不继续扩大修改范围。

1. 列出实际修改文件，确认没有超出约定目录。
2. 运行 [lint / typecheck / test / build 命令]，记录完整结果。
3. 在 [关键页面] 的 [视口列表] 检查溢出、遮挡、换行、对齐、主题和组件状态。
4. 对照 [设计规范、token 版本或改造前截图]，区分预期差异、非预期差异和无法判断项。
5. 实际操作 [关键任务]，检查键盘、焦点、加载、失败恢复、权限和回调行为。
6. 汇总已通过、失败、未覆盖、需人工确认和建议回退的项目。
7. 不要因为构建通过或静态扫描数量下降就宣布视觉和体验全部通过。

三类必须停止的情况

  • 规范来源或版本相互冲突。
  • 修改可能改变业务逻辑、权限、公共 API、埋点或数据语义。
  • 视觉差异无法解释、映射无法确认，或没有可回退的基线。

遇到这些情况，AI 应输出人工决策清单，而不是继续扩大修改。

十二、让 AI 长期理解项目设计规则

单次提示词适合解决一次任务。长期治理需要把下面内容写入 Design Tokens、组件规范、项目说明文件或 Skill：

  • 规则来源与版本；
  • 适用目录、页面和技术栈；
  • 颜色、排版、间距、组件状态和主题的语义；
  • 设计稿、代码和文档的映射方式；
  • 合理例外与禁止自动修改的区域；
  • 构建、测试、截图和人工检查命令；
  • 变更、迁移、弃用和删除条件；
  • 冲突、权限和无法判断时的停止条件。

一份好的 Skill 是项目工作手册，不是流行风格清单。它能降低重复解释成本，让 AI 的行为更容易审查，但无法替代设计师对品牌、信息层级和局部取舍的判断。

十三、三类角色如何分工

角色主要责任不能交给 AI 单独决定的内容
UI/UX 设计师定义视觉与体验标准，处理例外，验收结果品牌取舍、信息层级、体验质量
产品经理明确业务规则、优先级和成功标准权限、状态、失败处理和业务影响
前端工程师控制技术边界，审查实现，维护测试与回归能力架构、性能、兼容性、公共 API 和发布风险
AI扫描、归纳、生成方案、执行受控修改、运行检查最终产品判断和上线责任

设计师的工作重点会更多落在规则、判断和验收上。前端减少的是重复样式劳动，增加的是对 AI 代码和全局影响的审查。产品需要把“大一点”“更有质感”这类描述转成可以确认的业务目标和体验标准。

十四、常见组合路径

视觉与组件双轨诊断 → 分流

并行运行场景 3 和场景 7，得到视觉、布局、语义、API 和 A11y 的问题地图。评审后把问题分为立即修复、规则建设、迁移清理、待产品确认和合理例外。

提纯或 Token 试点 → 主题与 Redesign

视觉暂时不变时先运行场景 4；已有外部 token 时先运行场景 8。基础变量稳定后，再用场景 5 更新页面和基础组件。每一步都保留截图与回退点。

资产迁移 → 组件迁移 → 旧版本下线

先完成图标和图片映射，再迁移废弃组件 API。两类迁移都通过首批页面验证后，才扩大范围。旧资产和旧组件要等使用方清零、文档更新和回归完成后再删除。

响应式或交互问题 → 局部修复 → 版本治理

场景 1、2、6 解决当前问题；如果同类问题持续出现，就把规则、组件或文档纳入设计系统治理机制，避免每次只做一次性补丁。

结语

AI 可以加快 UI 扫描、修改和验证，但它不会自动理解项目真正需要的设计。提示词的价值，在于把任务范围、事实来源、权限、产物和验收标准说清楚。

当设计稿、token、组件、页面、资产和版本变化都能被追踪时，AI 才能从一次性的改页面工具，变成进入真实产品流程的 UI 治理助手。

对设计师来说，值得建立的能力不是让 AI 无限扩大修改范围，而是把设计判断转化成可以审计的规则，把规则拆成可以执行的任务，再用真实页面和用户操作确认结果。
